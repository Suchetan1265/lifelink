00How to use this

Read it once end to end, then use section 13 as a drill.

The single most valuable thing you have is that you built this. Interviewers can tell within two minutes whether a project on a CV was understood or merely followed. The difference is never the technology list; it is whether you can say why you chose one thing over another and what you would do differently.

01The system in one page

Learn to describe this in ninety seconds. It is the opening of every interview where the project comes up.

LifeLink matches blood donors to hospitals. A hospital raises a request; the system finds nearby donors with a compatible blood group and notifies them; if nobody confirms before a deadline that depends on urgency, the request escalates to blood banks holding stock. 

Browser (React)
      |  HTTPS, JWT in an Authorization header
      v
Spring Boot API  --------> PostgreSQL   the source of truth
      |          --------> Redis        geo index, caches, rate limit
      |          --------> RabbitMQ     email / SMS / push fan-out
      |
   Quartz jobs: escalate (15m), expire (15m), eligibility (daily)

The sentence that makes it sound designed rather than assembled: "PostgreSQL is the only thing that must be up. Redis and RabbitMQ are accelerators, and every path through them degrades instead of failing." That single idea organises most of this guide.

02Authentication

Proving who you are. Distinct from authorization, which is what you may do.

The problem it solves

HTTP is stateless: every request arrives with no memory of the last one. So each request must carry proof of identity. The old answer was a session — the server stores who you are and gives you a cookie holding a lookup key. That works, but every server instance then needs access to that session store, which becomes a bottleneck and a shared dependency.

JWT: a token that carries its own proof

A JSON Web Token is three base64 segments separated by dots: a header, a payload of claims (who the user is, when it expires), and a signature. The server signs the first two parts with a secret key. When the token comes back, the server recomputes the signature; if it matches, the payload was not tampered with.

The consequence is the whole point: the server does not need to store anything. Any instance holding the secret can verify any token. That is what makes JWT scale horizontally.

Common trap

A JWT is signed, not encrypted. Anyone can read the payload by base64-decoding it. Signing prevents modification, not reading. Never put anything secret in a JWT. Saying this unprompted marks you out immediately.

Why access tokens are short-lived, and what refresh tokens fix

Because nothing is stored server-side, a JWT cannot be revoked — it is valid until it expires. If someone steals a token valid for 30 days, they have 30 days of access. The fix is to make access tokens expire fast, and issue a second long-lived refresh token whose only job is to obtain new access tokens. The refresh token is stored server-side, so it can be revoked.

Rotation makes this stronger. Each time a refresh token is used, it is revoked and a new one issued. If an attacker steals one and uses it, the real user's next refresh fails — which is both a lockout and a detectable signal that something is wrong.

In LifeLink
  • Access token: JWT, HS256, 15 minutes, claims are user id, role, email.
  • Refresh token: 256 bits of randomness, 7 days, rotated on every use.
  • Refresh tokens are stored as a SHA-256 hash, never in plain text — a database leak yields nothing usable.
  • Passwords use BCrypt.
  • Resetting a password or disabling an account revokes every refresh token for that user.

Why BCrypt and not SHA-256 for passwords

This is the most common interview question in the whole area. SHA-256 is designed to be fast — billions of hashes per second on a GPU, which is exactly what an attacker with a stolen password table wants. BCrypt is deliberately slow and has a tunable work factor, so you can make it slower as hardware improves. It also salts every password automatically, so two users with the same password get different hashes and one cracked password does not reveal others.

The general rule: fast hashes for integrity, slow hashes for passwords. BCrypt, scrypt and Argon2 are the slow family.

OAuth and "Sign in with Google"

OAuth 2.0 lets a user prove their identity to you via a provider they already trust, without you ever seeing their password. In the flow LifeLink uses, the browser asks Google for an ID token — itself a JWT, signed by Google — and posts it to the backend. The backend verifies it against Google's public keys.

Verification is three checks, and a candidate who names all three sounds senior:

  1. Signature — against Google's published JWKS, proving Google issued it.
  2. Issuer — that iss is Google and not somebody else.
  3. Audience — that aud is your client id. Without this check, a token minted for any other Google app would be accepted, which is a complete authentication bypass.
In LifeLink

A first-time Google user gets an account with no donor profile, because a Google identity says nothing about blood group, location or travel radius. The client sends them to a short form before the dashboard becomes reachable. Their password hash is set to a random unusable value rather than null, so ordinary password login simply fails instead of needing a special case.

Password reset done safely

Three properties matter, and each has a reason:

  • Single-use and time-limited — a link leaked from an inbox months later is worthless.
  • Stored hashed — same argument as refresh tokens.
  • Always answers "sent", whether or not the address exists. Otherwise the endpoint becomes a way to discover who has an account, which is called user enumeration.

LifeLink also revokes every session on reset: whoever prompted the reset may know the old password.

The interviewer asks

"Where do you store the JWT on the client, and why?"

There is no perfect answer, and they want to see you know the trade-off. localStorage is simple but readable by any injected script, so it is vulnerable to XSS. An httpOnly cookie is invisible to JavaScript, but cookies are sent automatically, which opens CSRF unless you add SameSite or a token.

Say which you chose and why. LifeLink uses localStorage, accepting XSS exposure for simplicity, and mitigates the blast radius with 15-minute access tokens. Naming the mitigation is what turns a weak answer into a considered one.

03Authorization

Given that we know who you are, what are you allowed to do?

Authentication happens once per request, at the edge. Authorization happens continuously and at several depths, and conflating the two is a classic junior mistake.

Two layers, and why one is not enough

Role-based access control answers "is this user a HOSPITAL?" That is coarse. It does not answer "is this their request?" — which is ownership, and it is where real breaches happen.

A system that only checks roles has an insecure direct object reference bug: hospital A requests /api/requests/42, passes the role check because it is a hospital, and reads hospital B's data.

In LifeLink
  • Role at the controller: @PreAuthorize("hasRole('HOSPITAL')").
  • Ownership in the service: every request load goes through loadOwnedRequest(), which throws if the request belongs to another hospital.
  • State in the lifecycle: a hospital cannot confirm a donor who has not accepted, however legitimate the hospital.

Three independent gates. The client also hides screens by role, but that is convenience, not security — anyone can call the API directly, which is why every check is repeated server-side.

The interviewer asks

"Your frontend hides the admin page from non-admins. Is that secure?"

No, and the answer should be immediate. Client code runs on the user's machine and can be modified; the API is the real boundary. Client-side guards exist so people do not see broken screens. Then give the example: LifeLink's admin routes are role-guarded in React and enforced with @PreAuthorize, and the second one is the one that matters.

04Databases and migrations

Why a relational database here

The data is deeply relational — donors, hospitals, requests, matches, donations — and correctness matters more than raw write throughput. Relational databases give you foreign keys (a match cannot point at a request that does not exist), unique constraints (a donor cannot be matched twice to the same request), and transactions.

In LifeLink

PostgreSQL over MySQL, for three concrete features rather than preference: partial indexes, TIMESTAMPTZ for unambiguous instants across zones, and built-in trigonometric functions used by the fallback distance query.

Indexes, and the partial index worth mentioning

An index is a lookup structure that turns a full-table scan into a direct seek. The cost is space and slower writes, since every insert must update the index too. So you index what you filter on, not everything.

A partial index covers only rows matching a condition: 

CREATE INDEX idx_donors_available_by_group
  ON donors(blood_group) WHERE available = true;

Matching only ever looks for available donors, so indexing the unavailable ones would be wasted space and wasted write cost. The index is smaller, so more of it stays in memory. This is a genuinely good detail to raise unprompted.

Migrations: version control for your schema

A migration is a numbered SQL file describing one schema change. The tool records which have run, so every environment converges on the same schema by applying the same files in the same order. Without this, production schemas drift and nobody can reproduce a bug.

The rule: migrations are append-only. Never edit one that has run anywhere. Write a new one.

In LifeLink

Flyway owns the schema; Hibernate runs ddl-auto: validate, which checks that entities match and refuses to start otherwise. Three migrations: V1__init, V2__escalation_accepting_bank, V3__password_reset.

Using ddl-auto: update in production is a well-known way to lose data — Hibernate guesses at changes and will happily do the wrong thing. validate turns schema drift into a startup failure, which is where you want to find it.

05Transactions

A group of operations that all succeed or all fail.

Recording a donation writes a donation row, closes the request, and sets the donor's 90-day cooldown. If the second write fails after the first succeeds, you have blood recorded against an open request and a donor who never went on cooldown. A transaction makes the three either all happen or none.

ACID is the property set: Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent transactions do not see each other's half-finished work), Durability (committed means survives a crash).

In LifeLink

@Transactional on service methods. Spring wraps the method in a proxy that opens a transaction before and commits after, rolling back on a runtime exception.

Some internal methods use Propagation.MANDATORY, which means "refuse to run unless a transaction already exists" — a compile-time-ish guarantee that the matching engine can never be called outside one.

Common trap

@Transactional does nothing when a method calls itself. Spring implements it with a proxy that wraps the object. An internal call goes direct to the instance and bypasses the proxy entirely, so no transaction starts. This surprises almost everyone once, and interviewers love it.

06Caching and Redis

Keep a copy of expensive answers somewhere fast.

What Redis is

An in-memory data store. Because it never touches disk on the read path, lookups are sub-millisecond where a database query might be tens of milliseconds. Unlike a plain key-value cache it has real data structures: lists, sets, sorted sets, hashes, counters and geospatial indexes — which is why it is used for far more than caching.

The three things Redis does in LifeLink

KeyStructurePurpose
donors:geo:{group}GEO setNearest available donors per blood group. Not a cache — an index.
donor:{id}:profileJSON, 1h TTLA genuine read cache.
stats:adminJSON, 5m TTLCaches an expensive multi-aggregate query.
rl:requests:{id}Counter, 1h TTLRate limiting. Not a cache at all.

Note that only two of the four are caches. Saying "we used Redis as an index, a cache and a counter, and those are three different problems" is a much stronger answer than "we used Redis for caching".

Geospatial search, and why the database was the wrong place

"Find donors within 15 km" naively means computing the distance from the hospital to every donor and filtering — a full scan with trigonometry per row, which gets slower as you grow. Redis GEO sets store points in a sorted set keyed by a geohash, so nearby points sit near each other and a radius query becomes a range scan.

In LifeLink

The interesting part is that Redis alone was not enough. Redis knows where donors are; it does not know that a donor is already committed to another request. So matching is a hybrid: Redis narrows by geography and blood group, then a single SQL query filters those candidates by the rules only the database knows.

"Redis narrows, PostgreSQL decides" is the sentence to remember.

Cache invalidation, and the write-through discipline

The hardest part of caching is knowing when a cached copy is wrong. Two broad strategies:

  • Cache-aside — check the cache; on a miss, read the database and populate. Simple, but stale until the TTL expires.
  • Write-through — update the cache at the moment the underlying data changes. More work, but never stale.

Membership of the geo index means "matchable right now", which four different events can change. All four write through immediately: the availability toggle, a profile edit that moves a donor or corrects their blood group, a recorded donation starting a cooldown, and the daily eligibility job ending one.

In LifeLink

A profile edit removes the donor from all eight group sets before re-adding, so a corrected blood group cannot leave a stale entry in the old one.

And the detail worth leading with: the whole index is rebuilt from PostgreSQL on every startup. Without that, a flushed Redis would silently shrink the pool of reachable donors with no error anywhere — the failure looks exactly like "no donors nearby", which is the most dangerous kind of bug: silent and plausible.

The interviewer asks

"What happens when your cache and database disagree?"

Answer with the principle first: one system is the source of truth and the other is derived. PostgreSQL is authoritative; Redis holds a copy that can always be rebuilt from it. Then give the concrete mechanisms: write-through on every change, TTLs so nothing is stale indefinitely, and a full rebuild at startup so a wiped cache self-heals.

07Message queues and async work

The problem

A hospital raises a request and twenty donors need notifying. Sending twenty emails inline means the HTTP request takes as long as the slowest mail server, and if the mail provider is down, raising a request fails — for a reason that has nothing to do with raising requests.

A message queue decouples them. The API writes a message and returns immediately; separate consumers do the slow work. The API's latency no longer depends on email.

The vocabulary

  • Producer — publishes a message.
  • Exchange — receives messages and decides where they go.
  • Queue — holds messages until consumed.
  • Binding — a rule connecting an exchange to a queue.
  • Routing key — a label on the message that bindings match against.

A topic exchange routes by pattern, which is what lets one notification fan out to three independent channels.

In LifeLink

One topic exchange notifications, routing keys notify.email, notify.sms, notify.push, one durable queue per channel. Email and push get everything; SMS costs money, so it is reserved for types someone must act on quickly.

Retry: 4 attempts, 2s initial, doubling, capped at 30s. Exhausted messages are rejected, not requeued, so they land on a dead-letter queue instead of looping forever.

Dead-letter queues

A DLQ is where messages go when they cannot be processed. Without one you choose between losing the message and retrying it forever — and infinite retry of a message that can never succeed is a classic way to take down a consumer. A DLQ makes failure inspectable.

The subtle bug worth telling a story about

In LifeLink

Publishing originally happened inside the transaction. That is wrong, and the reason is worth understanding: if the transaction rolls back after the message is published, you have emailed twenty donors about a request that does not exist.

The fix is to publish after commit, using a transactional event listener. It is a small change that demonstrates you think about ordering and failure, and it is a genuinely good interview story because the bug is invisible until it happens.

The interviewer asks

"What if a message is delivered twice?"

Most brokers guarantee at-least-once delivery, not exactly-once — so duplicates are a fact of life and consumers should be idempotent: processing the same message twice has the same effect as once. For LifeLink a duplicate means a duplicate email, which is tolerable. Say what the consequence would be in your system and whether you accepted it. Claiming exactly-once is a red flag; it is famously close to impossible in a distributed system.

08Scheduled jobs

Work that happens because time passed, not because someone asked.

Nobody clicks a button to expire a request. It expires because its deadline passed. That kind of work needs something that wakes up on a schedule and looks for things to do.

In LifeLink
JobScheduleWork
Escalationevery 15 minRequests past their urgency window become ESCALATED; nearby banks alerted
Expiryevery 15 minRequests past needed-by become EXPIRED
Eligibilitydaily 00:05Donors off cooldown are notified and re-indexed

Two design points that make jobs safe

Deadlines live in one place. The per-urgency windows (2h critical, 6h high, 24h normal) are fields on the Urgency enum, and the job filters in Java rather than encoding intervals in SQL. Encoding them twice means a new urgency level is silently ignored by the job. Single source of truth beats a marginally faster query.

Jobs are catch-up, not replay. If the app is down for an hour, three 15-minute windows are missed. LifeLink does not replay them, because each run re-reads whatever is still overdue — running once catches everything. That is a misfire policy, and knowing the term is useful.

The interviewer asks

"You scale to three instances. What happens to your scheduled jobs?"

This is the question on scheduling, and the honest answer is best. All three fire, so the job runs three times concurrently — which for LifeLink could escalate the same request three times and send triplicate alerts.

The fixes: Quartz supports a clustered JDBC job store where instances coordinate through the database so only one runs each trigger; or take a distributed lock; or move scheduling outside the app entirely. LifeLink uses an in-memory store and runs one instance, which is a deliberate limit rather than an oversight — and saying that is much stronger than pretending it scales.

09Designing for failure

The section that most separates SDE1 from SDE2 answers.

Junior designs assume dependencies work. Senior designs decide, for each dependency, what happens when it does not — and make that a deliberate choice rather than an accident.

Fail closed or fail open?

Fail closed means denying the operation when a check cannot run — safe, but unavailable. Fail open means allowing it — available, but unprotected. Which is right depends entirely on what the check protects.

In LifeLink

The rate limiter fails open. If Redis is down, the request is allowed. The reasoning: a hospital with a genuine emergency must never be blocked because a cache is unavailable. Losing the cap for the length of an outage is the cheaper failure.

An authentication check would fail closed — you never let someone in because the check was unavailable. Same principle, opposite answer, because the stakes are reversed.

FailureBehaviourCost
Redis downMatching falls back to SQL; caches miss to the database; limiter fails openSlower, no rate cap
Redis flushedRebuilt from PostgreSQL at next startupNone
RabbitMQ downPublish logs a warning; in-app notifications unaffectedEmail and SMS only
PostgreSQL downThe application is downTotal, and deliberately so

That last row matters. Not everything should degrade. PostgreSQL is the source of truth; serving from a stale cache with no authority behind it would be worse than an error page. Knowing which dependency is allowed to be fatal is itself a design decision.

In LifeLink

A real consequence of this design: the health endpoint aggregates Redis and RabbitMQ, so with either unreachable it reported DOWN — and the hosting platform would have restart-looped a perfectly serving app. The fix was a health group covering only the database. The readiness signal has to match what the app genuinely requires.

10Docker and deployment

What a container actually is

"It works on my machine" happens because machines differ — Java version, libraries, settings. A container packages the application and its environment into one image that runs identically anywhere.

A virtual machine emulates hardware and runs a whole guest OS: heavy, slow to start. A container shares the host kernel and isolates only the process: megabytes, starts in a second. That distinction is a very common interview question.

An image is the template; a container is a running instance. Images are built in layers, and layers are cached — which is why Dockerfiles put rarely-changing steps first.

Multi-stage builds

Building needs a JDK, Maven and Node. Running needs only a JRE and a jar. A multi-stage build compiles in a fat builder image, then copies just the artifact into a slim runtime image — the final image never contains the compiler or source. 

FROM maven:3.9-eclipse-temurin-17 AS build
COPY backend backend
COPY frontend frontend
RUN mvn -f backend/pom.xml -Pwebapp package -DskipTests

FROM eclipse-temurin:17-jre
COPY --from=build /build/backend/target/*.jar app.jar
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=55", ...]
In LifeLink

The React build is packaged inside the Spring Boot jar, so one service serves the UI and the API from one origin. That removes CORS entirely and halves the hosting footprint. Trade-off: you cannot redeploy the frontend without restarting the backend.

The container runs as a non-root user, so a compromise inside it does not start with root.

Configuration and the twelve-factor idea

Config that differs between environments — database URLs, secrets — belongs in the environment, not the image. One image is then promoted unchanged from test to production, so what you tested is exactly what ships.

In LifeLink

JWT_SECRET has no default, so the app refuses to start without it. A default would be published in the repository, and any deployment that forgot to override it could have tokens forged against it. Failing loudly at startup beats running insecurely.

The interviewer asks

"Why is your container memory configured the way it is?"

Because the JVM and the container disagree about memory unless you tell them not to. A 512 MB container with a heap set to 75% leaves too little for metaspace, code cache and thread stacks — the container gets OOM-killed with nothing useful in the logs. LifeLink uses 55% plus SerialGC, which has lower overhead at small heap sizes. This kind of answer reads as production experience.

11Testing

The kinds, and what each is for

  • Unit — one class, dependencies mocked. Fast, precise, but proves nothing about how pieces fit.
  • Integration — several real components together. Slower, and catches what unit tests cannot.
  • End-to-end — the whole system, usually through the UI. Slowest and most brittle.
In LifeLink

50 tests, nearly all integration: they boot the real app against a real embedded PostgreSQL, not H2 and not mocks. The reason is specific — the project uses partial indexes, TIMESTAMPTZ and native SQL, none of which H2 reproduces faithfully. A test suite that passes on H2 and fails on PostgreSQL is worse than no suite.

Testcontainers is the usual answer, but it needs Docker, which the development machine did not have. Embedded PostgreSQL runs a real server with no Docker at all.

The decision worth explaining in an interview

In LifeLink

Most tests run with Redis and RabbitMQ deliberately absent. That sounds like laziness and is the opposite: those are the fallback paths, so running the suite without them keeps every degradation path continuously covered. A change that makes a Redis call non-optional fails the build rather than surfacing during an outage.

A separate, smaller suite runs against a real embedded Redis for the cases that must prove the Redis path itself works.

Common trap

Shared state makes tests order-dependent. When a feature was added so donors are matched the moment they become available, four existing tests broke — donors started claiming other tests' open requests before their own were raised. The fix was to give each test its own patch of the globe, so nothing overlaps. "My tests passed individually but failed together" is a great, honest story about test isolation.

The interviewer asks

"What would you do differently?"

Never say "nothing". Real answers, all defensible:

  • No frontend tests. 50 on the backend, none on React. Given time, component tests for the matching and confirmation flows.
  • Spring State Machine is an unused dependency. Either adopt it or remove it; leaving it is the worst of both.
  • Scheduled jobs do not survive scaling out. Fine for one instance, would need a clustered store or a lock.
  • Donor coordinates are exposed to the requesting hospital so it can plot the map. An approximate location until the donor is confirmed would be kinder.

13Mock interview

Answer out loud. If an answer takes more than ninety seconds, it is not sharp enough yet.

Opening

  1. Describe LifeLink in ninety seconds.
  2. Which part was hardest, and why?
  3. Draw the architecture on a whiteboard and explain the data flow of one request.

  1. What is inside a JWT, and what stops someone editing it?
  2. Why two tokens instead of one?
  3. Someone steals a refresh token. What happens, and how do you find out?
  4. Why BCrypt rather than SHA-256?
  5. Your API returns another hospital's request. Which check failed?
  6. How do you verify a Google ID token, and what breaks if you skip the audience check?

Data

  1. Why a relational database here rather than MongoDB?
  2. What is a partial index and why did you use one?
  3. Why does Hibernate run in validate mode?
  4. Walk through recording a donation. What must be atomic, and why?

Caching and queues

  1. Why Redis for geo search rather than a SQL distance query?
  2. Redis is wiped in production. What happens?
  3. How do you keep the cache from going stale?
  4. Why publish notifications after commit rather than during?
  5. A consumer keeps failing on one message. What happens to it?
  6. Your broker is down. Is the app still usable?

Operations

  1. Difference between a container and a VM?
  2. What does a multi-stage build buy you?
  3. Why does the app refuse to start without JWT_SECRET?
  4. Your health check reports DOWN but users are served fine. What went wrong?
  5. You scale to three instances. What breaks first?

The closing question

"What would you do differently?" — prepare three specific answers with reasons. This question separates people who built something from people who followed a tutorial, and it is almost always asked.
