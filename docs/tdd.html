1Problem and scope

Blood is perishable, demand is spiky, and the people who can supply it are scattered and mostly unaware they are needed.

When a hospital runs short, the current process is phone calls: to blood banks, to donor registries, to individuals. Nobody knows who is nearby, who is medically eligible today, or who has already committed to somewhere else. LifeLink closes that gap by holding donor availability and location as live state, and turning a hospital's shortage into targeted notifications within seconds.

In scope

  • Donor registration, availability, and the 90-day recovery period between donations.
  • Hospital requests with urgency, automatic donor matching, and a confirm-then-record handover.
  • Blood bank stock and an escalation path for requests no donor takes in time.
  • Administrative verification of hospitals and blood banks before they can act.
  • In-app, email, SMS and push notification channels.

Explicitly out of scope

  • Medical screening. Eligibility here is the 90-day interval only. Real deferral criteria — medication, travel, weight, haemoglobin — belong to the collecting clinician, not this system.
  • Blood typing. The donor's stated group is trusted; the platform never verifies it and the collecting site must.
  • Cold chain and logistics. Units are counted, not tracked.
  • Payments. Donation is unpaid.

The safety posture. LifeLink is a coordination layer, not a clinical one. Every irreversible physical act — drawing blood, releasing stock — is performed and recorded by a verified organisation, and the audit trail records who did what and when.

3Architecture

One Spring Boot application, three supporting services, and a strict rule about which one is authoritative.

     Quartz ── escalation (15m) ── expiry (15m) ── eligibility (daily)

The load-bearing rule

PostgreSQL is the only authority. Redis is a derived index that can be rebuilt from it at any time, and RabbitMQ carries copies of facts already committed. This single rule is what lets every other component fail without taking the platform with it, and it is why the GEO index is rebuilt from the database on every startup.

Package layout

Organised by feature rather than by layer, so a change to blood banks touches one directory: admin, auth, bloodbank, common, donor, hospital, job, messaging, notification, redis, request, security, user.

5Request state machine

Every status change goes through one method, which rejects illegal transitions, stamps timestamps and writes the audit row.

Design note: why not Spring State Machine

The dependency is present but unused. The transition table is a Java enum where each event carries its legal source states and its target, and RequestLifecycleService validates against it in about forty lines. Spring State Machine would add a configuration class, a persister and a runtime per request to express the same table. This is a deliberate deviation from the original specification, recorded here rather than hidden: either adopt the library properly or drop the dependency.

Guards

  • A hospital cannot confirm a donor whose match is not ACCEPTED.
  • A donation cannot be recorded against a donor who was not CONFIRMED.
  • A blood bank cannot release stock it does not hold, and only the bank that accepted the escalation may fulfil it.
  • A donor holds at most one live commitment across the whole platform.

6Matching engine

Two entry points — a request being raised, and a donor becoming available — reaching the same rules.

Push: when a request is raised

  1. Compute the compatible donor groups for the requested group.
  2. GEORADIUS each group's set around the hospital, merge and sort by distance.
  3. Narrow the candidate ids in PostgreSQL: still available, still eligible, and not already tied to an active request — a fact only the database holds.
  4. Drop anyone whose own travel radius does not reach the hospital.
  5. Take the nearest 20, write request_matches rows, notify each.

Redis narrows, PostgreSQL decides. The geo search is the expensive part and belongs in Redis; the correctness filters stay in the database. If Redis is unreachable, or returns nothing because it was flushed, the whole match falls back to a Haversine query in SQL.

Pull: when a donor becomes available

Matching originally ran only at request creation, which meant a donor who registered or switched availability on a minute later never heard about a request that was still open and needed exactly their blood group. Turning availability on, or coming off cooldown, now attaches the donor to the best open request they can reach — most urgent first, then nearest, and only one.

Browse

Donors can also list every open request their group can serve inside their radius and volunteer directly. Browsing deliberately ignores the availability toggle, because looking at what is needed is how someone decides to switch it on.

Compatibility

Held in one enum with two derived views: compatibleDonors() answers "who can supply this patient" for the push path, and canDonateTo() answers "who can this donor help" for the browse path. Deriving the second from the first means the two can never disagree.

7Caching and Redis

KeyTypeTTLPurpose
donors:geo:{group}GEO setnoneAvailable, eligible donors per blood group. The matching hot path.
donor:{id}:profileJSON1 hourThe donor's own dashboard read.
stats:adminJSON5 minThe admin dashboard aggregate, which is several grouped counts.

Write-through discipline

GEO set membership means "matchable right now". Four events can change that, and all four write through immediately: the availability toggle, a profile edit that moves the donor or corrects their group, a recorded donation starting the cooldown, and the daily eligibility job ending it. A profile edit removes the donor from all eight sets before re-adding, so a corrected blood group cannot leave a stale entry behind.

Cold start

DonorGeoBootstrap rebuilds every set from PostgreSQL on startup. Without it, a flushed Redis would silently shrink the donor pool with no error anywhere — the most dangerous failure mode in the system, because it looks like "no donors nearby".

Deviation from spec. donor:{id}:profile was specified as a cache for match ranking. Ranking has to reach PostgreSQL regardless, to exclude donors already committed, so a profile cache would save nothing there. It caches the donor's own dashboard read instead, which is a genuine hot path.

8Messaging and RabbitMQ

One notification becomes up to three deliveries, each independently retryable.

Topology

  • Topic exchange notifications, routing keys notify.email, notify.sms, notify.push.
  • One durable queue per channel, each with a dead-letter exchange and its own .dlq.
  • Listener retry: 4 attempts, 2s initial interval, doubling, capped at 30s. Exhausted messages are rejected, not requeued, so they land on the dead-letter queue instead of looping.

Two decisions worth recording

Publishing waits for the commit

The notification row is written inside the business transaction; publishing happens on a @TransactionalEventListener bound to after-commit. Without this, an operation that rolls back after calling notify() would still send email about something that never happened — reachable in practice, since several services notify before a lifecycle transition that can throw.

Messages carry ids, not addresses

The payload is the notification id, user id, type, title and body. Workers resolve the current email or phone at delivery time, which keeps stale contact details out of the queue and keeps the matching hot path free of extra lookups when notifying twenty donors.

Channel policy

Email and push receive everything. SMS costs money, so it is reserved for types someone must act on quickly: a new match, a confirmation, an escalation, a cancellation. The SMS worker skips silently when no phone is on file.

9Scheduled jobs

JobScheduleBehaviour
RequestEscalationJobEvery 15 min Requests still RAISED or MATCHED past their urgency window move to ESCALATED; every verified bank within 50 km of the hospital is alerted.
RequestExpiryJobEvery 15 min Requests past needed_by and not yet fulfilled move to EXPIRED; the hospital is told.
DonorEligibilityJobDaily 00:05 Donors whose cooldown ends today are notified, returned to the GEO index, and matched to an open request if one fits.

Deadlines live in Java, not SQL

The per-urgency windows — CRITICAL 2h, HIGH 6h, NORMAL 24h — are fields on the Urgency enum, and the jobs load non-terminal requests and filter in memory. Encoding the intervals in SQL would duplicate them, and a new urgency level would then be silently ignored by the job. The working set is bounded by open requests, not by table size.

Misfires are handled with next-with-remaining-count: a window missed during downtime is not replayed, because all three jobs are catch-up by nature — they re-read whatever is still overdue.

10Authentication and authorisation

  • Access token — JWT, HS256, 15 minutes, carrying subject, role and email.
  • Refresh token — 256 bits of randomness, 7 days, stored as a SHA-256 hash. Presenting one revokes it and issues a fresh pair, so a stolen token is usable at most once before the legitimate holder's next refresh fails visibly.
  • Passwords — BCrypt.
  • Authorisation — a stateless filter populates the security context; @PreAuthorize guards each controller by role, and services re-check ownership so a valid token for the wrong hospital still fails.

Verification as a gate

Donors are usable immediately; hospitals and blood banks are created PENDING and refused until an administrator approves. Anyone can claim to be a hospital, and a hospital can summon a stranger to an address — the gate is the control that makes the rest of the platform safe to operate.

Secrets

JWT_SECRET has no default: the application refuses to start without it. A default would be published in the repository, and any deployment that forgot to override it could have tokens forged against it. Local convenience lives in an explicit dev profile that cannot be active by accident.

11Epics and stories

The epic decomposed into stories, each with the acceptance criteria that were actually implemented and tested.

E1 · Identity and access

E1-S1

Register as a donor

As someone willing to give blood, I want an account, so that hospitals can reach me.

Acceptance
  • Email, password, blood group, location and travel radius are captured; the account is active immediately.
  • Availability starts off — registering is not consent to be called today.
  • A duplicate email is rejected with 409.
E1-S2

Register as an organisation

As a hospital or blood bank, I want to register, so that I can use the platform once verified.

Acceptance
  • Account is created PENDING; sign-in works but privileged actions are refused with 403.
  • Hospitals must supply a licence number for the administrator to check.
E1-S3

Sign in and stay signed in

As any user, I want my session to survive longer than the access token, without staying valid forever if stolen.

Acceptance
  • Login returns a 15-minute access token and a 7-day refresh token.
  • Refresh rotates: the presented token is revoked and a new pair issued.
  • Logout revokes; a disabled account cannot refresh.
  • The client refreshes once on a 401 and retries, with concurrent 401s sharing one refresh.

E2 · Donor lifecycle

E2-S1

Control availability

As a donor, I want one switch that decides whether I can be called on.

Acceptance
  • Turning it on adds the donor to the GEO index; off removes them.
  • Turning it on also attaches them to the best open request they can reach, if any.
E2-S2

See where I can donate

As a donor, I want to see every open request I could serve, not only what I was sent.

Acceptance
  • Lists open requests my group can serve within my radius, most urgent first.
  • Works regardless of the availability toggle.
  • Volunteering counts as an acceptance and moves the request to MATCHED.
  • A second commitment is refused with 409 while one is live.
E2-S3

Respond to a match

As a donor, I want to accept or decline a request I was notified about.

Acceptance
  • The first acceptance moves the request RAISED → MATCHED; the hospital is notified.
  • Responding twice is refused; responding to another donor's match is refused.
  • Declining leaves the request open to others.
E2-S4

Recover between donations

As a donor, I want the platform to know I cannot give again yet.

Acceptance
  • A recorded donation sets last donation date and next eligible date 90 days out.
  • The donor leaves the GEO index and is not matched while on cooldown.
  • Eligibility shows days remaining; history lists past donations.

E3 · Hospital request lifecycle

E3-S1

Raise a request

As a hospital, I want to state what I need and how urgently.

Acceptance
  • Requires verification; unverified hospitals are refused with 403.
  • Matching runs synchronously and donors are notified on submit.
  • Capped at 10 per hospital per hour, returning 429 beyond that.
E3-S2

Watch responses

As a hospital, I want to see who was contacted and what they said.

Acceptance
  • Lists each donor with NOTIFIED / ACCEPTED / DECLINED and distance.
  • Polls every 10 seconds while the request is open; plots donors on a map.
E3-S3

Confirm a donor

As a hospital, I want to commit one specific person so they travel.

Acceptance
  • Only available for a donor whose match is ACCEPTED; otherwise 409.
  • Request moves to CONFIRMED; that donor receives address and needed-by time.
  • Other accepting donors are told the request is covered.
E3-S4

Record the donation

As a hospital, I want to record that blood was actually given.

Acceptance
  • Only after a donor is CONFIRMED; exactly one of donor or blood bank is supplied.
  • Writes the donation, closes the request FULFILLED, starts the donor's cooldown.
E3-S5

Cancel, and see the trail

As a hospital, I want to call it off, and later see exactly what happened.

Acceptance
  • Cancellation is allowed from any non-terminal state and requires a reason.
  • Committed donors are told not to come.
  • Every transition appears in a timeline with actor, reason and timestamp.

E4 · Blood banks and escalation

E4-S1

Maintain inventory

As a blood bank, I want to keep units per group current.

Acceptance
  • All eight groups are always returned, zero-filled, so the editor is a full grid.
  • Updates upsert only the groups supplied.
E4-S2

Take on an escalated request

As a blood bank, I want to cover a request no donor took.

Acceptance
  • Only ESCALATED requests within 50 km are listed, with my stock for that group shown.
  • Accepting moves the request to CONFIRMED and locks it to my bank; a second bank gets 409.
  • Releasing stock decrements inventory and closes the request; insufficient stock is refused with nothing deducted.
  • A bank that did not accept cannot fulfil, receiving 403.

E5 · Administration

E5-S1

Verify organisations

As an administrator, I want to approve or reject registrations.

Acceptance
  • Queue filterable by hospital or blood bank; approving activates immediately.
  • Rejecting disables the account, revokes its refresh tokens and sends the reason.
  • Approving a rejected account reactivates it; approving twice returns 409.
E5-S2

Watch platform health

As an administrator, I want to know whether the platform is working.

Acceptance
  • Requests by status, fulfilment rate, average hours to fulfil, donors by group and city, pending verifications.
  • Cached 5 minutes; a Redis outage degrades to an uncached query rather than an error.
E5-S3

Suspend an account

As an administrator, I want to stop an abusive account.

Acceptance
  • Disabling blocks sign-in and revokes refresh tokens.
  • An administrator cannot change their own status.

E6 · Notifications

E6-S1

Be told what happened

As any user, I want to see what the platform has told me.

Acceptance
  • In-app notifications written synchronously with the work that caused them.
  • Email, SMS and push published after the transaction commits.
  • A broker outage costs a delivery, never the in-app record.

E7 · Client

E7-S1

Give a location without typing coordinates

As anyone registering, I want to set my location the way people actually think about places.

Acceptance
  • Browser geolocation, place-name search, or dropping a pin on a map.
  • The resolved address is shown back so the pin can be checked.
  • A refused permission or unreachable search explains the alternative rather than failing silently.
E7-S2

See only my role's screens

As any user, I want an interface scoped to what I can actually do.

Acceptance
  • Routes are role-guarded on the client and enforced again on the server.
  • Signing in lands on that role's home screen.

12Failure behaviour

What each dependency failing actually costs. This table is the design, not an afterthought.

FailureBehaviourCost
Redis downMatching falls back to the SQL Haversine query; caches miss through to the database; the rate limiter fails open.Slower matching, no request cap for the outage.
Redis flushedRebuilt from PostgreSQL at next startup; an empty GEO result triggers the SQL fallback rather than reporting no donors.None, if the app restarts.
RabbitMQ downPublishing logs a warning and continues; in-app notifications are unaffected.Email, SMS and push for the outage.
Delivery keeps failingFour attempts with backoff, then dead-lettered per channel.Inspectable, not lost.
PostgreSQL downThe application is down.Total — and deliberately so, since nothing else is authoritative.
Missing JWT_SECRETStartup fails.Deliberate: better than running on a published key.

The rate limiter failing open is worth naming as a decision rather than an accident. A hospital with a genuine emergency must never be locked out because a cache is unavailable; losing the cap for the length of an outage is the cheaper failure.

13Testing strategy

43 backend tests, almost all of them booting the real application.

Real infrastructure, no Docker

Tests run against an embedded PostgreSQL — a real server, not H2 — so Flyway migrations, partial indexes and native SQL are exercised exactly as written. An embedded Redis covers the cases that must prove the Redis path itself works.

Most tests run with Redis and RabbitMQ absent

This is deliberate. It keeps every degradation path continuously covered, so a change that makes a Redis call non-optional fails the suite rather than surfacing during an outage.

SuiteCovers
AdminVerificationFlowTestThe verification gate end to end, double approval, rejection disabling sign-in, role isolation, stats.
DonorJourneyTestAvailability, match, accept, confirm, fulfil, 90-day lockout, response guards.
DonationOpportunityTestBrowse listing, compatibility, radius, urgency order, single-commitment rule.
LateAvailabilityMatchingTestA donor becoming available after the request was raised.
BloodBankEscalationFlowTestEscalation, offer radius, accept locking, stock guards, expiry.
RedisMatchingAndLimitsTestGEO membership, Redis-backed matching, rate limit, both caches.
NotificationDispatchTestAfter-commit publishing, and that a rollback publishes nothing.
SeedDataTestThe demo dataset loads into a clean database.

Tests share one database, so each works in its own patch of the globe. Once donors began claiming open requests eagerly, assertions started depending on execution order. Giving each test method its own latitude band was the fix — cheaper and more honest than truncating tables between tests.

14Frontend

React 18 on Vite, with TanStack Query doing most of the work.

  • Session — tokens in local storage; an Axios interceptor refreshes once on 401 and retries. A single in-flight refresh is shared, since parallel 401s would otherwise each rotate the refresh token and leave all but one holding a revoked one.
  • Polling — request detail every 10s while open, lists every 15–20s, notifications every 30s. Simpler than websockets for this volume.
  • Guards — role-scoped routes, enforced again server-side.
  • Bundle — Leaflet and Recharts are each used on one screen, so both are split out; the shared bundle is 147 kB, 50 kB gzipped.

Design language

A clinical crimson accent with red-biased neutrals, so greys sit with the accent rather than fighting it. Status is encoded as a chip everywhere it appears, using one colour scale shared between the app and this documentation. Illustration is drawn — an ECG trace on the sign-in panel — rather than photographic, which keeps the payload small and the theme coherent.

15Open items

  • Spring State Machine is an unused dependency. Adopt it properly or remove it.
  • No frontend tests. The build, dev server and API path are verified; no screen is driven in a browser.
  • Blood banks have no per-bank service radius, so escalation uses a fixed 50 km. A column and an editor would make it real.
  • Notification delivery is not verified end to end against a live broker; the workers are covered by unit tests and the publisher by an integration test.
  • Deployment is not automated. No pipeline, no infrastructure as code.
  • Donor coordinates are exposed to the requesting hospital so it can plot who is coming. Defensible, but a real deployment should consider showing an approximate location until the donor is confirmed.
